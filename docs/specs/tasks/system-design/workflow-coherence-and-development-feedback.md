# Workflow coherence and development feedback

This task spans workflow definitions, task recovery, inbox projection, view configuration, session history, and agent instructions. The contracts below are the technical design for task `cff7923a-b870-4e72-bf9b-6470d6b9c350`. The task plan owns delivery order and commands. Existing task requirements remain authoritative; implementation must reconcile each contract with its owning system specification before changing production code.

## Verified baseline

- Local YAML import in `internal/workflow/service/service.go` creates or skips by name. Only `ApplySyncedWorkflows` updates an existing workflow, and it selects GitHub-sourced workflows by path and name. Its step reconciliation matches names; a rename allocates another step ID and removal with assigned tasks skips the update.
- Startup reconciliation in `internal/orchestrator/service.go` settles running sessions to `WAITING_FOR_INPUT`, moves an `IN_PROGRESS` task to `REVIEW`, and stamps `interrupted_at`. `possible-question-triage.ts` labels any interrupted Review as `stale_review`, regardless of age.
- The Role Pipeline prompt in `docs/examples/role-pipeline.workflow.yml` requires a design and plan but gives both overlapping verification content. The example must remain byte-equivalent to `scripts/update-live-role-pipeline.py`; the live workflow updater guards against user-edited prompts.
- Kanban renders one grouped lane set per workflow. `applyViewGroup` is single-level, and the repository-group lane label omits workflow identity, so repeated labels appear. Current view filters/groups persist in user settings; sidebar saved views provide a named-view CRUD precedent.
- `task_sessions.workflow_step_id_at_creation` is immutable context. Step visit lists in `activity_service.go` read destination sessions only from `task_session_routes`; ordinary new sessions, handoffs, and recovery launches do not write that ledger. Step visits are derived from transitions and entry sequence, rather than stored as one durable visit row.
- Backend test setup is dominated by compile/link in focused runs; web Vitest startup and CI worker setup are similarly material. The existing Makefile supplies `-trimpath -tags fts5`, while some agent instructions omit them.

## Workflow file update contract

Add an explicit update operation addressed by **workspace ID and existing workflow ID**. A local file remains client-read YAML sent as text using the current import parser and profile-binding resolution. A file containing multiple workflows requires an explicit selection; never infer a target solely from its name. The preview returns a normalized structural diff for workflow settings, step order, step attributes, transitions, event actions, profile bindings, and agent instructions. Show old and new values for modified fields and report parse, reference, profile, and compatibility errors before confirmation.

Preview is read-only and returns an opaque version token derived from the stored workflow and steps. Apply reparses and revalidates the supplied definition, checks the token inside the write transaction, and rejects a changed source or target with a conflict that requires another preview. Update the selected workflow in place. Preserve its workflow ID and source ownership; a Git-synced workflow remains read-only to this manual operation until explicitly released from sync. Share validation, conversion, step diff, and reconciliation logic with repository sync, while keeping Git source discovery and deletion policy separate.

Step identity must be explicit. Extend the portable format with a stable step key for matching; exports emit it and legacy files can still match an unchanged unique name. A rename without a stable key or explicit old-to-new mapping is ambiguous: preview blocks apply and asks for a mapping, rather than guessing by position. Matched renames retain the database step ID. Removal of a step referenced by any current task, queued launch, active session, or step-primary mapping blocks apply with affected counts and a remediation choice. Historical transitions, routes, decisions, and sessions remain resolvable to the retained step row; they must not display as an unrelated new step. Recheck all references at apply time. The reconciler commits all changes atomically or none.

### I1 persistence and transaction decision

The workflow repository owns a `workflow_steps.portable_key` unique within a workflow and a nullable `retired_at` on the same row. Add portable export version 3 with `StepPortable.key`; v3 exports always include the key, while v1/v2 remain readable. Backfill existing rows with generated opaque keys, not names or positions. A copy imported as a new workflow may reuse the same portable keys because uniqueness is workflow-scoped. An unchanged unique name is the compatibility match for a keyless v1/v2 update. A rename in such a file requires an explicit mapping of old step ID to new name in the confirmed update request; reject ambiguous, duplicate, mismatched, or retired keys. Never recycle a retired key or step ID. The workspace/workflow ID, not portable name or key, chooses the update target.

The workflow subsystem owns the identity schema contract, but both repositories must install it before their first workflow-step write. The task repository creates a projection `workflow_steps` table and bootstraps built-in steps before `workflow/repository.NewWithDB` runs in production; task-only fixtures do the same without constructing the workflow repository. Extract the portable-key/retirement columns, backfill, and unique index into one idempotent workflow-owned schema helper with a single migration implementation. Call it from task repository initialization after its projection table exists and before built-in workflow inserts, and from workflow repository initialization after its table exists. The helper must handle old tables with neither column and new tables with both, work on SQLite and PostgreSQL, and make failures fatal before any inserts. Keep the workflow repository's domain reads and writes as their current owner; do not duplicate the new migration SQL in task and workflow packages. Add task-only, workflow-only, and production startup-order tests.

Retirement, not deletion, is the file-update removal operation. A retired `workflow_steps` row remains addressable by its original ID, name, key, and workflow, along with its participant and decision references. Active workflow/step lists, transitions, selectors, and new associations exclude retired rows; history resolvers may read them. Do not mutate a retired row's historical label or configuration. A normal delete path must obey the same historical retention rule before it is reused by file update. If current task placement, queued target, running session at the step, live step-primary selection, or an inbound executable step reference exists, reject file-update retirement with affected counts; an archived task still placed at that step is a current placement until reassigned. Existing manual DeleteStep queue cleanup may continue, but its retained-row operation must remain atomic and its result must not be used to bypass the stricter file-update gate. Historical transitions/routes/decisions and completed sessions do not block retirement. A workflow whose own deletion would cascade retained steps must remain protected by its existing task/history deletion policy; expanding whole-workflow deletion is outside I1.

`workflow/repository` owns a single `ApplyWorkflowDefinition` transaction over the shared writer database. The service parses, resolves profiles, constructs the full diff and candidate outside the transaction; the repository then locks the selected workflow, reloads source/ownership and all active steps, compares a canonical version digest of persisted workflow and step fields (including keys and retirement), rechecks active references, and writes workflow fields, step updates/creates/retirements, and executable-reference cleanup before commit. It returns one conflict/error or one committed result; broadcasts and profile-rebinding logs run only after commit. SQLite's writer transaction serializes competing writes. For PostgreSQL, task moves, queue assignments, and session starts that can create a live reference must take the same workflow-row lock before writing; otherwise retirement is disabled on PostgreSQL until that lock protocol exists. The adapter must not call independently committing task or workflow service methods from inside this operation. Git sync should call the same repository reconciliation transaction with its source policy, not its current split-write loop. A no-drift update performs no write or broadcast.

The revision is deliberately narrower than the preceding paragraph's snapshot/tombstone option: retaining the row preserves the original identity and existing participant FK without duplicating historical state. See [ADR-2026-10-09-workflow-step-identity-and-atomic-update](../../../decisions/2026-10-09-workflow-step-identity-and-atomic-update.md).

## Recovery and inbox contract

Keep persisted task state distinct from the execution's last outcome. The task-owned [recovery and Review episode contract](recovery-review-episodes.md), owned by `REQ-TASKS-RECOVERY-REVIEW-001`, records one typed interruption episode per affected session and one Review-entry episode per task. Startup and periodic recovery settle only lost execution; restart alone never writes Review. The task repository writes Review identity, timestamp, and origin in the same transaction as an actual state entry. The existing `interrupted_at` marker remains a warning compatibility projection. Legacy uncertainty is explicit: ambiguous session ownership stays task-level, and an old Review row gets an observed-at-migration baseline rather than a fabricated entry date. Clear an interruption only after correlated successful recovery; an unresolved sibling retains the warning.

Startup cleanup of an already `FAILED` session likewise preserves the task state and exposes the existing typed failure; it does not create Review or an interruption episode. A separate, genuine Review entry remains intact.

Project inbox categories from durable task/session state and structured reason codes, with one highest-priority actionable row per task/session incident: pending user question, interrupted and resumable, failed execution, provider quota/unavailable, genuinely awaiting review, aged review, and external dependency. Quota and provider labels require typed failure data; unknown errors stay generic. Review age is computed on a timer from its authoritative entry or conservative observation baseline, never `updated_at`. Episode IDs keep acknowledgements and deduplication stable across restarts; repeated reconciliation cannot create a duplicate. Rows explain their reason and link to the corresponding resume, retry, answer, review, or dependency action. Preserve the existing Failed tab and clarification authority; consolidate presentation and deduplication rather than creating a competing state machine.

## View and grouping contract

Persist named presets in the existing user-settings contract, scoped to view and workspace as appropriate, storing the existing filter clauses and an ordered group-key list. Reuse saved-view CRUD semantics: stable ID, name, create/apply/update/rename/delete, active ID, and a dirty indication when current settings differ. Preserve current single-group settings by migrating them to one-element lists on read; provide a reversible settings migration and no loss of filters. Apply is immediate, while saving is explicit. Enforce a bounded preset count and stable ordering.

The grouping engine accepts an ordered sequence of extractors and yields a tree whose node identity is the encoded full path of typed keys. A repository-group-only view groups tasks globally once per group, including a single unassigned group. Repository-group then workflow nests workflows under each group. ## Session-to-visit association contract

The task repository owns one mutable session-to-visit association. The detailed contract is [session step visits](session-step-visits.md), owned by `REQ-TASKS-SESSION-VISITS-001`. A visit is projected from an existing committed destination transition, or from a clearly labelled current-state activation baseline when no evidenced entry exists. Future visits are written atomically with task moves and ledger rows. Never reconstruct or backfill a `task_step_transitions` row: pre-activation history is unknown, and legacy sessions without one uniquely evidenced interval remain unassigned. `workflow_step_entries` is not the universal visit identity because manual moves do not allocate it. Do not overwrite `workflow_step_id_at_creation` or rewrite historical routes when a user reassigns a session.

At session creation, including manual creation, handoff, and recovery, associate to the task's current visit in the same durable transaction. An explicit override selects an eligible visit; a step-only choice resolves to its current/latest visit only when unambiguous and the UI shows the visit when a step was revisited. The session-tab action changes this association through a task-scoped API with optimistic validation that the visit belongs to the same task. The activity summary and step hover menus read the same association and include historical visits, even if a step later becomes a tombstone. A removed step cannot receive a new association; existing historical associations remain readable. Step-primary selection is separate and cannot silently change the visit.

## Transition failure diagnostics contract

`REQ-TASKS-TRANSITION-DIAGNOSTICS-001` covers synchronous moves and asynchronous workflow advancement. One task-domain classifier builds a `TransitionFailure` from the typed cause and a fresh, task-scoped state snapshot. It is the only source of code, public message, reason list, actionability, and remediation. Each reason carries a stable rule identifier; optional criterion/step IDs and description; observed and required state; a concrete next action; and an optional safe CTA kind/target. Preserve existing top-level codes, especially `task_completion_gate_blocked`, and add fields rather than changing the successful response shape. Unknown causes use a stable internal-failure code and incident reference with a safe retry/support action, never a raw internal error. Authorization failures reveal no inaccessible task or workflow details.

For a completion gate, use the same snapshot as the gate authority, not a separate UI heuristic. Return each blocker and unverified criterion with ID and description, gate revision, enrolled plan revision ID/write version, current plan head revision ID/write version, and whether a fresh approved enrollment or criterion verification is the next step. A plan-head mismatch gets the explicit action “request approval for the current revision, then re-enroll its increments”; a current enrollment with unmet criteria gets “verify these increments with evidence.” Do not offer a move or manual override as the routine agent remedy. The classifier also covers invalid/unknown named edge, stale source step, target absence or foreign workflow, task/workspace permission, archived/terminal state, active-session conflict, WIP/capacity, invalid entry options, changed task or plan revision, external dependency, and transient persistence/provider failure. An error with multiple independent failed rules returns every applicable reason in a deterministic order.

MCP `move_task_kandev` and `step_complete_kandev`, HTTP move/state endpoints, and WebSocket move/transition responses serialize the same envelope (`code`, `message`, `reasons`, `actionability`, `remediation`, `incident_id` when needed) in their native error wrapper. The MCP wrapper must preserve structured details in agent-visible tool content. `step_complete_kandev` can accept a signal before asynchronous advancement; acceptance remains distinct from transition success. If later advancement or a deferred move fails, persist a task-scoped failure outcome tied to move/signal ID and publish an existing task event or additive diagnostic event so the originating session, later agent turn, and UI can read it after reconnect. Clear/replace it only when that attempt is resolved or superseded. Do not report an accepted signal as a completed move.

The task UI consumes the shared wire type through one error presenter. Manual drag/drop, stepper, named-transition controls, and workflow-change submission show a localized headline plus expandable specific reasons after rollback. Keep the failure visible in the task panel as a banner when a toast would expire; a safe CTA opens the relevant plan, criterion, session, dependency, or retry control. User-actionable and operator/system failures have distinct labels. On phone, the banner is inline in the task view; details open in a touch-accessible drawer with one scroll owner and safe-area clearance, following `mobile-menu-sheet.tsx`. No details depend on hover. Do not expose raw server text or secret state as copy. Existing code-to-localization mapping remains as a fallback for older backends.

## Cross-boundary safeguards

The workflow update and session-association changes share step identity: implement stable keys and historical resolution before allowing destructive step edits. Recovery classification must be tested with startup and periodic reconciliation; no UI-only heuristic may imply a task entered Review. User-facing copy goes through i18n in all supported locales. Run targeted backend, frontend, migration, and browser tests for changed behavior. Stop if a preview can apply to a changed target, a session points to another task's visit, removed steps lose history, or restart produces a duplicate or misleading review item.
